### Recovery from inconsistent role-deletion reads

The writer assignment was removed and Azure Activity Log recorded the exact role-definition
DELETE as `Succeeded`/`OK`. The helper and its EXIT retry nevertheless reported failure at their
post-delete absence checks. A later unchanged-helper retry returned `no role definition`, but a
subsequent full role list again contained the same original definition, failing the strict final
invariant. No writer was regranted and neither the apply nor the repeat job was rerun.

Read-only diagnostics saved CLI lists, raw ARM lists, exact-definition GETs, status codes, and
request headers. These service reads disagreed: a raw list could include the deleted definition
while the CLI list omitted it and an exact GET returned HTTP 404 `RoleDefinitionDoesNotExist`.
An exact GET also briefly returned HTTP 200 again without a new creation. Three samples separated
by 15 seconds agreed on CLI/raw-list absence and exact GET 404 about 9 minutes 22 seconds after
the successful deletion event. The unchanged Step 9 then passed in full.

Optional reader cleanup reproduced the same issue independently. Instrumented calls showed that
its unchanged helper returned success after two empty absence reads, while the next full role list
still included the deleted reader. Activity Log confirmed a successful DELETE. Three CLI/raw-list/
exact-GET samples finally agreed about 7 minutes 56 seconds afterward. A final read-only sweep
then confirmed zero identity role assignments, zero owned definitions in both list APIs, HTTP 404
for both exact deleted role GUIDs, and unchanged inherited shared custom-role definitions.

This is observed service read inconsistency, not proof of a missing delete permission or a
runbook failure. Microsoft states that [custom-role deletion can take a few minutes](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles-portal#delete-a-custom-role);
it does not promise this test's convergence time. The helpers and source pin were preserved.
The guide now explains how to keep the original evidence, verify the exact deletion, wait for
consistent reads, and repeat only final inspection. Its absence checks were not weakened.

## Publication defect and correction

The original helper used `az automation runbook replace-content --content @file`. Inspection of the
installed CLI's `_expand_file_prefixed_files` and `_load_file` path showed `rstrip(os.linesep)`.
The fetched published content was exactly the source with its final LF removed. This is an
observation of the tested CLI version, not a claim about when that behavior was introduced.

| Content | Bytes | SHA-256 |
|---|---:|---|
| Original source | 56,508 | `2cef45acc81b04a6bbcd62582db6f974102ae98f2de79231a90907f49a7dd555` |
| Original CLI upload, fetched after publication | 56,507 | `3eb14042b6433a395d7e4de95c54959f7f5fe342bc472f65ee19bad1c47262f7` |
| Corrected upload, fetched draft and published content | 56,508 | `2cef45acc81b04a6bbcd62582db6f974102ae98f2de79231a90907f49a7dd555` |

The fix sends `curl --data-binary` to the documented
[runbook draft-content PUT](https://learn.microsoft.com/en-us/rest/api/automation/runbook-draft/replace-content?view=rest-automation-2024-10-23).
It passes the access token through curl's stdin configuration, follows an accepted asynchronous
operation, and checks the draft hash before linking the runtime and publishing. The final
published-state, runtime, and content-hash gates remain in place. Substituting `az rest --body @file`
would reuse the same CLI file-expansion behavior.

The eight publisher regression tests cover exact UTF-8 content with CRLF and multiple final
newlines, synchronous and asynchronous success, operation-header precedence, untrusted or missing
operation URLs, HTTP rejection, failed operations, and draft-content mismatch. The 45-scenario
runbook behavioral harness, static validation, cleanup-trap regression, shell syntax, Bicep, JSON,
and public-content privacy checks also passed.
