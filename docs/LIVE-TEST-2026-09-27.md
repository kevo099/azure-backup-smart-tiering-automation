# New-tenant combined-guide live test — 2026-09-27

**Result: the combined Policy + Automation guide passed in a brand-new tenant on a Free Trial
subscription, and the runbook completed its first live write to a backup policy that protects a
real VM.** Guide sections 1–8 passed with two deviations that the environment required: a
different Automation region, and one extra VM size needed only by an optional extension. The
Automation canary repeated the 2026-09-06 checkpoints: exact publication, a pre-RBAC 403 with no
`SUMMARY`, reader readiness on the first job, the exact seed, audit `1/0/0`, bounded apply `1/1/1`,
idempotent repeat `0/0/0`, and writer removal. An optional extension then protected one private
test VM and ran the runbook against its policy. Both protected-policy guards skipped the policy.
With the documented `AllowWriteWithoutETag=true` override inside an exclusive test window, the
apply changed only the policy's `ArchivedRP` tiering mode. That write returned `202` and is the
first recorded live run of the runbook's asynchronous-tracking branch.

This qualifies an agent-executed replication, not an observed human study. It does not qualify
archive-tier movement, restore, V2/hourly, tagged or multi-item policies, Resource Guard/MUA, or
production-scale behaviour; see [Evidence boundary](#evidence-boundary).
The Policy side of the same run, including the validation-only Deny probes, is recorded in the
Policy repository's
[2026-09-27 new-tenant record](https://github.com/kevo099/azure-enterprise-policy-baseline/blob/main/docs/LIVE-TEST-2026-09-27-new-tenant.md).

## First write to a policy protecting a real VM

This optional extension went beyond the guide. It ran after section 8 had passed.

### Setup

- A private `Standard_D2als_v7` Ubuntu 24.04 VM in East US 2 with no public IP.
- A dedicated Recovery Services vault in the VM's region. It reported soft delete state `AlwaysOn`
  as soon as it was created, and that state cannot be disabled. Microsoft's
  [secure-by-default soft delete](https://learn.microsoft.com/en-us/azure/backup/secure-by-default)
  article states that all newly created vaults have soft delete permanently enabled. Storage
  redundancy was set to `LocallyRedundant` before any item was protected (see
  [CLI observations](#cli-observations)).
- One Azure VM V1 daily policy retaining daily points for 30 days, weekly for 12 weeks, monthly
  for 12 months, and yearly for 2 years. Its retention horizon was 24 months, and it started at
  `ArchivedRP` `DoNotTier`.
- The VM was protected with that policy, then an on-demand backup was submitted.

### Runbook results

Every job used the exact `VaultName` and `PolicyName`, `ExpectedMatches=1`, and `MaxChanges=1`.
Counts are candidates/submitted/verified.

| Step | Parameters | Observed result |
|---|---|---|
| Protected-item guard | `MaxProtectedItemsPerPolicy=0` | `SkippedProtectedItemsExceedLimit`; `0/0/0`; no write |
| Concurrency-token guard | `MaxProtectedItemsPerPolicy=1`, no override | `SkippedNoConcurrencyToken`; `0/0/0` |
| Audit with override | plus `AllowWriteWithoutETag=true` | `WouldEnableTierRecommended`; `1/0/0` |
| Temporary writer | RG-scoped remediator granted | — |
| Apply | same, `Apply=true` | `EnabledAndVerified`; `1/1/1` on the first attempt; the PUT returned `202` and was followed through `Azure-AsyncOperation` to `Succeeded` |
| Idempotent repeat | same | `AlreadyCompliant`; `0/0/0` |
| Writer removal | revoke | Writer verified absent; only the discovery reader remained |

Both guard jobs ran with `Apply=false`. They record the same classification that an apply run
evaluates before its first write. The concurrency-token guard fired because the policy body
carried no `eTag` member; the runbook reads only that body member, not response headers. A separate
operator check of the `backupPolicies` GET (api-version `2025-08-01`) found no ETag in the body or
the response headers for any policy checked in that vault, including the protected one. The
override was used only inside an exclusive test window, with a single operator and a dedicated
policy.

After the write:

- a normalized before/after comparison showed no non-tiering policy property changed;
- `protectedItemsCount` stayed `1`, and the item was still protected by the same policy.

The apply's PUT returned `202`. The runbook followed `Azure-AsyncOperation` to `Succeeded` and then
verified the policy; the job's evaluation and verification rows were about a minute apart. This is
the first live write recorded in this repository to take that asynchronous branch, which was
previously covered only by the offline harness. The empty-canary apply earlier in the same run
completed synchronously with HTTP `200`. The run does not show why the two writes differed.

### Side effects of the policy write

- Azure started a `ConfigureBackup` job on the protected item right after the policy write, and
  the job completed in about 10 seconds. This is consistent with the README's note that a policy
  update is re-applied to every protected item. Microsoft's
  [crash-consistent backup article](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-agentless-multi-disk-crash-consistent#option-2-modify-the-backup-policy-to-change-from-applicationfile-system-consistent-backup-to-crash-consistent-backup)
  also shows Configure backup jobs triggered for each VM in a policy after the policy is modified
  in the portal. The policy protected only one item, so per-item scaling was not measured.
- The on-demand backup had been submitted before the write. It was still running during the write
  and completed afterwards (about 26 minutes, one recovery point). The item therefore had no
  completed recovery point when the policy changed. This run did not test a policy whose items
  already hold mature recovery points.

### CLI observations

- `az backup vault backup-properties set` ignored `--backup-storage-redundancy` when it was
  combined with `--soft-delete-feature-state`, and warned that the "parameters will be ignored".
  This is deliberate in Azure CLI `2.90.0`: whenever a soft-delete argument is supplied, the command
  ignores the redundancy, cross-region-restore and alert arguments, and it does not change the soft
  delete state of an `AlwaysOn` vault. Setting `LocallyRedundant` in a separate call worked before
  any item was protected.
- `az backup protection backup-now` rejected the `properties.containerName` value returned by
  `az backup item list` with `BMSUserErrorContainerNameIncorrectFormat`. Passing the VM name as both
  the container name and the item name, with `--backup-management-type AzureIaasVM --workload-type VM`,
  worked. The command's help says `--container-name` takes the `Name` or `FriendlyName` from
  `az backup container list`, and that a friendly name requires the backup management type.

## Cleanup and final state

- Protection was stopped with delete-data. Under the vault's `AlwaysOn` soft delete, the item
  became soft-deleted with a 14-day hold.
- The VM, its OS disk, and its NIC were deleted. Section 8 was re-run and passed.
- The VM vault was created in the combined showcase's resource group. It is being kept until the
  soft-delete hold expires (about 14 days), and this run did not attempt to delete it. Until then,
  group-level cleanup of the showcase, such as the combined guide's coordinated cleanup, may be
  refused or may leave a soft-deleted vault record; see the next item.
- Microsoft's pages differ on what deleting such a vault does. The
  [vault-deletion article](https://learn.microsoft.com/en-us/azure/backup/backup-azure-delete-vault#before-you-start)
  and the [soft delete FAQ](https://learn.microsoft.com/en-us/azure/backup/soft-delete-azure-backup-faq#can-i-delete-my-vault-if-there-are-soft-deleted-items-in-the-vault-)
  say that a vault holding soft-deleted items can't be deleted until those items are permanently
  removed. The [secure-by-default article](https://learn.microsoft.com/en-us/azure/backup/secure-by-default#soft-delete-for-vaults)
  says that deleting such a vault from the Azure portal moves it into a soft-deleted state instead. Neither path was tested.
- The combined showcase remains deployed, as the guide intends. Its Automation identity holds only
  the RG-scoped discovery reader, and no temporary writer remains.

Costs were not measured.

## Evidence boundary

- The run was agent-executed in one Free Trial subscription. It was not an observed human study.
- The following were not qualified: archive-tier movement, restore, V2/hourly policies, tagged
  policies, multi-item policies, Resource Guard/MUA, and production-scale discovery or writes.
- The protected-policy write used `AllowWriteWithoutETag=true` in an exclusive window. It does not
  make concurrent writers safe. Keep the fail-closed default for protected policies.
- The run followed the combined guide, which uses this repository's pinned helpers. The standalone
  [walkthrough](replicate-in-azure.md) was not run separately. The offline harness ran on local
  PowerShell 7.6 under the combined guide; the walkthrough's Step 0 still requires 7.4 and was not
  re-qualified. The storage-account smart-tier repository was not exercised.
- Raw job output, policy documents, and identifiers remain in the operator's private evidence
  directory outside this repository. Only sanitized results and public source hashes are recorded
  here.
